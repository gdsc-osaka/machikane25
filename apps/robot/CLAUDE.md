# Codex駆動開発 共通ガイドライン

思考は英語で行い、最終的な出力は必ず日本語で提供してください。

## Codexの基本姿勢
- 指示の優先順位（System > Developer > User > Repository Docs）を常に確認し、矛盾があれば即座に共有する
- 依頼の背景と成果物を最初に整理し、必要に応じて確認質問で意図合わせを行う
- 作業が複雑な場合は計画を提示し、完了した手順ごとに更新して透明性を保つ
- 与えられた制約（サンドボックス、ネットワーク、時間）を意識して実行可能な代替策を探る
- プロジェクトのフェーズに応じて品質・スピード・安全性のバランスを判断し、意思決定理由を明示する

## コマンドとファイル操作
- `shell` 実行時は `["bash","-lc", "<command>"]` を基本とし、常に `workdir` を指定する（`cd` ではなくパラメータで指定）
- ファイル検索は極力 `rg` / `rg --files` を使用し、sandboxや権限が必要な操作は事前に理由を添えて申請する
- 破壊的コマンド（`rm`, `git reset --hard` 等）はユーザーからの明示的な指示がない限り実行しない
- 手動編集は `apply_patch` を優先し、自動生成が適切な場合はスクリプトやフォーマッタを活用する
- 既存の未コミット変更は尊重し、自分の作業範囲外の変更を勝手にリセットしない

## 応答スタイルと共有
- 途中経過・検証結果は必要十分に共有し、不要な出力は抑えて読みやすさを優先する
- 最終回答では変更点の意図→詳細→次の推奨アクションの順でまとめ、コマンドはバッククォートで示す
- ファイル参照は `path/to/file:line` 形式で行い、不要な巨大スニペットは貼り付けない
- 重要な判断や不確実性は明記し、未実施のテストがあればフォローアップ手順を提案する

## エラーハンドリングの原則
- 表面的な抑制ではなく根本原因を特定し、例外メッセージは原因と対処が伝わるように整備する
- 外部API・ネットワーク通信は常に失敗を想定し、タイムアウトやリトライの設計を行う
- エラーケースもテストで担保し、再発防止のために知見をドキュメント化する

## コード品質の基準
- DRY原則を守り、重複を排除して単一の信頼できる情報源を維持する
- 変数名・関数名・モジュール名は意図が自明になるように命名し、コメントは「なぜ」に限定する
- 小さな異臭も放置せず即時に整える（Broken Windowsを作らない）
- 2スペースインデントを守り、フォーマッタやリンタ（`pnpm lint:fix`）で整合性を確保する
- `const` をデフォルトとし、`let` / `var` は使用しない。命令形ループよりも関数型スタイル（`map`, `filter`, `reduce` 等）を優先する
- 型安全性を重視し、`as` による型アサーションは避けて型定義や型ガードで解決する

## リポジトリ固有の実装指針
- Next.js 13+ の約束事に従い、ページは `apps/stamp/src/app`、共通UIは `src/components` に配置する
- DDDではクラスを用いず、ドメインロジックは `src/domain` に純粋関数とプレーンオブジェクトで表現する
- アプリケーション層は `src/application`、インフラは `src/infra` に分離し、FireStoreのマッピングには `FirestoreDataConverter` を利用する
- データ取得はSWRベースのカスタムフックを用い、ミューテーションはサーバーアクションまたはAPI経由で再検証可能にする
- Tailwind 4のトークンとshadcn/RadixコンポーネントでUIを組み立て、インラインスタイルは避ける
- Firebaseの認証/ルール変更時は `apps/stamp/firestore.rules` と `.env.example` を更新し、秘密情報はコミットしない

## テスト規律
- TDDを徹底し、まず失敗するテストを書いてから実装を行う
- ユニットテストは実装ファイルと同階層の `__tests__/*.test.ts(x)` に配置し、統合テストは `apps/stamp/test/integration` にまとめる
- `pnpm test:stamp` と `pnpm coverage --filter stamp` で100%カバレッジを維持し、実行不能なテストを残さない
- Firestore/Authフローはエミュレータで検証し、外部連携（フォトブースAPI等）はスタブ化する
- テストは振る舞いにフォーカスし、副作用や共有状態に依存しないよう設計する

## 保守性とリファクタリング
- 機能追加と同時に既存コードの改善を検討し、必要なら技術的負債をドキュメント化する
- 大きな変更は小さなコミットに分解し、レビュー負荷とリスクを抑える
- 未使用コード・設定は排除し、依存関係はセキュリティと互換性の観点で定期的に更新する

## セキュリティ
- APIキーや資格情報は環境変数やシークレットマネージャで管理し、`.env.example` に必要な変数を追加する
- 外部からの入力値は常に検証し、最小権限の原則でサービスを構成する
- 不要な依存関係は追加しない。脆弱性診断ツールの実行結果は追跡し、改善計画を共有する

## パフォーマンス
- 推測ではなく計測に基づいて最適化し、ボトルネックの仮説はメトリクスで裏付ける
- 初期表示から逆算して遅延ロード・キャッシュ方針を設計し、N+1や過剰フェッチを避ける
- キャッシュの期限と無効化フローを定義し、負荷試験やプロファイル結果を記録する

## 信頼性
- クリティカルなI/Oにはタイムアウト・リトライ（指数バックオフ）・サーキットブレーカを組み合わせる
- ログとメトリクスで可観測性を確保し、障害時の調査を迅速化する
- 一時的な障害に耐えられるフェイルセーフとフォールバックの設計を検討する

## プロジェクトコンテキストの理解
- ビジネス要件と技術的制約の両方を踏まえ、最適な実装レベルを選ぶ
- 期限が厳しい場合でも最低限の品質基準を守り、妥協点は記録して後続タスクに残す
- チーム全体のスキルセットに合わせた技術選定・抽象度を心掛ける

## トレードオフの明確化
- 完璧を求めず、制約の中で最大の価値を届ける判断を行う
- プロトタイプ段階ではスピード、本番では堅牢性を優先し、その理由を記録する
- 影響範囲・リスク・未決事項を明文化し、関係者と認識を合わせる

## Git運用
- コミットは原子的に保ち、単一の意図に焦点を当てる
- コミットメッセージは短い命令形（例: `add stamp redemption flow`）で統一する
- main/masterへの直接コミットは行わず、レビュー可能なプルリクエストを作成する
- 変更の理由・テスト結果・関連チケットをPR本文にまとめ、影響範囲のレビュワーをタグ付けする

## コードレビュー
- レビューはコードにフォーカスし、建設的な改善提案としてフィードバックを受け取る
- 変更の背景・意図・影響範囲を説明し、代替案やリスクを率直に提示する
- フィードバックは学習機会として取り込み、必要な修正は迅速に反映する

## デバッグ
- 再現手順を明確化し、二分探索で原因箇所を絞り込む
- デバッガーやプロファイラ等のツールを適切に使い、調査ログを残す
- 原因と対処法を記録して共有し、同様の問題の再発防止に役立てる

## 依存関係
- 追加前にライセンス・メンテ状況・サイズを確認し、本当に必要なものだけ導入する
- ロックファイルを欠かさずコミットし、更新時は変更点と影響をレビューする
- セキュリティパッチやバグ修正が含まれる更新は優先的に対応する

## ドキュメント
- READMEにセットアップ・操作方法・依存関係を明記し、コード変更と同期して更新する
- 重要な設計判断はADRや `docs/spec/change-log.md` に記録し、実例を用いて説明する
- 変更が利用者に与える影響を文書化し、社内外のステークホルダーと共有する

## 継続的改善
- レトロスペクティブを定期的に実施し、プロセスを継続的に改善する
- 新しい手法やツールは小さく試し、効果とコストを評価して導入する
- 学びをドキュメント・ナレッジベースに蓄積し、チームの集団知を高める
